# Task-family evosearch with disagreement-based task selection

Evolutionary search (evosearch) over a **task family** instead of one task, plus one new step: after every round the
coordinator chooses **which task the next round evaluates on**, aiming at the task where the current candidate
programs disagree most. Disagreement is the source of useful information for the next round: when one program passes
and another fails on the same task, the diff between their code and traces localises the bug. A task where every
program passes (or every program fails) teaches little. Mutual information makes this precise (see "Disagreement").

Everything else is the existing evosearch loop (`scripts/tc1/evosearch_prompt.md`): K = 8 candidates per round, dev
seeds 51-65, parents chosen by `scripts/tc1/select_parents.py`, skill library frozen.

## The loop

```
round 0   task = family.round0 (fixed, identical in every arm)      candidates: 8 general programs
          eval 8 candidates on it, dev seeds 51-65                   (scripts/libero/evosearch_eval.py)
round N   parents_{N-1} = select_parents.py top3                     (unchanged)
          candidates_N written from the parents, using the traces of ALL tasks visited so far
          task_N = select_task(rule, history, candidates_N)         <- NEW: judges the programs about to be evaluated
          eval candidates_N on task_N, dev seeds 51-65
stop      after R rounds (default 5: iter_00..iter_04)
final     tournament: the last round's 3 parents on every family task, pick the best macro-average   <- NEW
held-out  that program on every family task, seeds 1-10 (families.json: heldout_seeds)
```

The task is chosen **after** the candidates of the round exist, so the committee whose disagreement is maximised is exactly the
set of programs that will be evaluated (not their parents). The candidate writer therefore does not know the task in advance;
it writes general programs from the traces of visited tasks.

Candidates are **general programs**: they read `env.handle.task_language` (an allowed API) and dispatch to skills, so
one program is meaningful on every task of the family. All candidates in a round see the same task, so their pass
rates are comparable inside a round; pass rates are **not** comparable across rounds (different tasks), which is why
the final pick needs the tournament instead of the single-task `select_parents.py best`.

## Task families

A family is a list of `(suite, task)` pairs in `families.json` (generated by `make_families.py`, names checked
against LIBERO). They span a relatedness axis on purpose: a weak relation makes selection harder and is a result in
itself.

| family | relation | tasks | what is shared / what varies | expected behaviour of selection |
|---|---|---|---|---|
| `bowl_stove_perturbed` | tight | 10 | one instruction; positions, language, extra objects, even the scene (floor / main table) | disagreement is nuisance-driven and concentrated in a few variants; little to gain, a sanity floor |
| `object_swap` | strong | 10 | identical skill (pick, place in basket); the object | disagreement from grasp geometry (bottles, boxes, cartons); neighbours in object shape behave alike |
| `spatial_swap` | strong | 10 | same object and goal; the spatial referring expression | disagreement from relational perception, not manipulation |
| `goal_swap` | medium | 10 | one scene; ten goals, different skills | main headline family: shared perception, partly shared skills |
| `drawer_ladder` | medium | 9 | drawer skills of growing composition length over two scenes | disagreement should rise with composition length; long tasks may all-fail |
| `three_suites` | weak | 12 | three scenes (goal / object / spatial swap), short tasks | tests whether descriptors predict disagreement across scenes |
| `mixed_short_skills` | weak | 12 | LIBERO-90 tasks from kitchen, living room, study: drawer, microwave, knob, pick-place, stacking | the hard case: prediction of disagreement must come from skill content |
| `libero10_long` | weak | 10 | long-horizon two-step tasks, many scenes | likely floor effect (all fail); only usable if the viability probe passes |

Recommended order: `goal_swap` first (headline), then `bowl_stove_perturbed` (tight) and `three_suites` or
`mixed_short_skills` (weak) to show how the benefit of selection moves with relatedness. `libero10_long` only after the probe.
Not used on purpose: the `*_task` suites (the runtime instruction is remapped, so static task text misleads).

### Viability probe (before spending a run on a family)
Run the family's starting program on every task x 3 dev seeds (about 3 trials per task). A family is viable when at
least a third of its tasks have a pass rate strictly between 0 and 1 for some program; if every task is all-fail or
all-pass there is no disagreement to select. The probe is **not** shown to any selector (it would make the arms unequal).

## Disagreement

For a task with committee outcomes `o[i][s]` in {0,1} (candidate i, dev seed s), K candidates, S seeds:

* `D_prog` = mean over pairs of `|p_i - p_j|` with `p_i` the pass rate of candidate i. Program-level disagreement.
* `D_seed` = mean over seeds of `H2(k_s / K)` with `k_s` the number of passing candidates, `H2` the binary entropy in bits.
  For deterministic outcomes this is the mutual information between the outcome and the candidate identity (BALD); it is
  maximal at a 50/50 split of the committee. **Primary metric.**
* `mixed_seed_frac`, `hamming_mean` (pairwise, normalised): descriptive.

Why `D_seed` is primary: trials are deterministic per seed (replays reproduce outcomes exactly), so a seed where some
candidates pass and others fail is a real contrast for the next round, and `D_prog` misses it when pass rates are equal.

## Selectors (the arms)

All write `iter_NN/task.json` through `scripts/taskselect/select_task.py`; the agent never edits `task.json`.

| rule | who decides | inputs |
|---|---|---|
| `random` | script, hash-seeded, without replacement | nothing (the control) |
| `prompt` | the coordinator LLM writes `iter_NN/task_choice.json` (task, predicted pass probability per candidate, rationale); the script validates and records it | committee programs, traces of visited tasks, perception-only descriptors of unvisited tasks |
| `harness` | the coordinator LLM writes a **proxy** `proxy.py` (a scoring function); the script runs it in a subprocess, takes the argmax over unvisited tasks, records every score | same inputs as `prompt`; the proxy file is hashed and locked (`proxy.lock.json`) so it cannot drift between rounds without `--unlock` being logged |
| `knn` | script, no LLM: Jaccard-similarity-weighted `D_prog` of visited tasks plus an exploration bonus (0.25 x distance to everything visited) | task descriptors + history; a simple non-LLM reference arm and backtest baseline, not the contribution |
| `probe` | script, from measurement: `probe-plan` runs the round's candidates on the first dev seed of every unvisited task; the task with the largest per-seed split wins (random fallback if nothing splits) | costs K x unvisited tasks trials per round, recorded in `task.json` |
| `oracle` | backtest only: picks the truly most-disagreeing task from a known outcome matrix | upper bound, not an online arm |

Descriptors are **perception-only**: the runtime instruction (`env.handle.task_language`) plus the reset-frame images
from `describe_tasks.py` (a `scene_snapshot.py` replay). Nothing from the simulator's internal state may reach a selector
(CLAUDE.md forbidden-API rule). The `prompt` rule asks for predicted pass probabilities so prediction quality is
measurable afterwards (Brier score, and correlation of predicted vs realised `D_prog`).

### What the harness proxy may and may not be
`score(ctx) -> {task_id: float}` where `ctx` has the descriptors, visited/unvisited ids, per-round committee outcomes,
code paths and parents. It runs in a subprocess with a timeout and a scrubbed environment (generated code is untrusted;
see the repo security boundary). It must be deterministic. Allowed ideas for the proxy: a surrogate success model per
program fitted on the visited tasks; similarity to tasks that already split the committee; a cheap partial run
(perception and grasp planning only) comparing the programs' intermediate plans.

## Controls and fairness

* Same `round0` task and **the same iter_00 candidates and results** in every arm: `select_task.py init-from` copies iter_00 from a
  reference run and records the provenance.
* Same model (`claude-sonnet-5`), K, dev seeds, rounds, parent rule, frozen skill library, isolation rules as the TC1 runs.
* The random arm uses the same pipeline; only the task choice differs.
* No task is evaluated twice in one run (selection is without replacement; `verify` enforces it).
* Repetitions: at least 3 per arm per family (the LLM-generated candidates are the dominant variance).
* Leakage: a harness proxy is designed from rounds the arm has already seen and then frozen. For offline backtests the
  proxy is designed on a split of the tasks and tested on the rest.

## Metrics and comparison

Per run: realised `D_prog` / `D_seed` of each round's task; best and mean dev pass rate per round; final tournament
macro-average; held-out macro-average over the family. Per arm pair: paired differences over repetitions with a bootstrap
confidence interval; the headline is final held-out macro-average and rounds to reach a target, **not** realised
disagreement alone (selecting disagreeing tasks is only worthwhile if the programs improve).

Offline backtest (`backtest.py`): given a candidates x tasks x seeds outcome matrix (`final-pick` writes a real one to `final/matrix.json`), replay a selector for a budget of B tasks and compare cumulative realised `D_prog` with the distribution of random
orders (many random draws) and the oracle. Reported: mean, bootstrap CI, fraction of random draws beaten.

## First measurements (goal_swap, 8 untuned round-0 programs, seeds 51-55, 2026-10-05)

* Matrix: 28 of 400 trials pass; 5 of 10 tasks are all-fail; two programs hold 24 of the 28 passes, on different tasks.
* Prediction from code and images alone is at chance (AUC 0.44 and 0.52 over two runs; both would pick an all-fail task).
  Given the round-0 results it is better but unstable (AUC 0.82 and 0.62; one run picks the best task, one an all-fail task).
* A one-seed probe ranks tasks by held-out `D_seed` with Spearman 0.80-0.92 and picks the best task for all five probe seeds.
* Cost-adjusted backtest, 5 rounds: probe 1.87-2.10 cumulative `D_seed`; random 0.88-1.02 at the same rounds and 1.31-1.51
  when given 2 extra rounds for the 240 probe trials.
* One family and one committee: not yet evidence that more disagreement gives better programs, which only online runs can show.

## Status and known limits

* On the planted synthetic family (`backtest.py --synthetic`) `knn` beats most random orders and trails the oracle clearly, so
  there is real headroom for a better proxy; it says nothing about real tasks until a real matrix exists.
* `knn` weights visited tasks by similarity but the committee changes every round, so old `D_prog` values describe older programs.
* The proxy subprocess limits accidents (scrubbed environment, temp cwd, timeout); it is not a security sandbox.

* Selection tooling, metrics, backtest and tests are implemented and run without a GPU. The online loop has not been run end to end.
* Image descriptors need the simulator; text-only descriptors work now and are what the offline tests use.
* The held-out stage is `families.json: heldout_seeds` per task (10 by default), not 50, to keep the cost sane; raise it for a final claim.
* A family-level starting program does not exist yet; iter_00 is written by the first run and copied to the other arms.
